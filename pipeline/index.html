Pipeline

From a benchmark to a diagnosis, in three modular stages — profile, evaluate, analyze.

An exploratory-QA task is a tuple τ = (Q, D, Dgold, T, A★, B): a question Q, a data lake D, the minimal gold sources Dgold sufficient to answer it, a tool set T (dataset search f(q,k) and data analysis g(c,d)), the gold answer A★, and a tool-call budget B (we use B = 30). SANA runs as three modules you can use independently:

1 sana-profiling → 2 sana-evaluation → 3 sana-analysis

1 sana-profiling

Profiling converts a benchmark into a LakeQA-style EQA task, then annotates it into a runtime profile that powers the idealized tools. A profile has three parts:

  • Source sequence — the ordered gold datasets needed for each subquestion.
  • Sanitized subquestions — subquestions rewritten so they don't leak which dataset to fetch.
  • Execution records — per dataset: the analysis intent, the query, and the verified answer.

KramaBench tasks (a monolithic question + solution script) are first decomposed into LakeQA-style sequential, dependent hops, each execution-verified against its intermediate answer. Example profile, adapted from a LakeQA task: 

{
  "task": "Compute the 2023 ratio of top-offense complaints to shootings in NYC's northernmost borough (rounded).",
  "source_sequence": ["The_Bronx", "nypd-complaints", "nypd-shootings"],
  "sanitized_subquestions": [
    "find NYC's northernmost borough",
    "count complaints there for the top 2023 offense",
    "count 2023 shootings there; divide (2)/(3), round"
  ],
  "execution_records": [
    { "src": "nypd-complaints", "intent": "count 2023 top-offense complaints in the Bronx",
      "query": "CNT(*) WHERE BORO='BRONX' & yr=2023 GRP_BY OFNS_DESC", "answer": 18613 },
    { "src": "nypd-shootings", "intent": "node_1_ans / 2023 Bronx shooting count",
      "query": "ROUND(18613 / CNT(*)) WHERE BORO='BRONX' & yr=2023", "answer": 42 }
  ]
}

Subquestion 1 only retrieves the The_Bronx dataset, so it has no execution record.

The profile is what each idealized tool draws on:

plan_ideal

Gives the gold sanitized subquestions as an explicit decomposition.

search_ideal

Always returns what the query wants from the task's gold source sequence (nothing irrelevant).

execute_ideal

Code has no implementation error and runs exactly as the agent intended when writing it.

# [FILL IN — exact CLI] profile a benchmark into runtime profiles
python -m sana.profiling --benchmark lakeqa --out profiles/

2 sana-evaluation

Evaluation runs an agent against the profiles while you choose which axis to ablate. Targeted ablations vary one axis and hold the others idealized, so there are no conflicting bottlenecks. Each run picks one mode per axis:

AxisModeDescription
PlanningNaiveNo planning tool; the agent answers directly.
StandardPlanning tool, but a self-written plan with no sanitized sequence.
IdealReceives the gold sanitized subquestion sequence.
SearchNaiveBM25 sparse lexical search over the lake.
StandardHybrid search (RRF) with LLM table descriptions (Pneuma / AutoDDG).
IdealAlways returns the query's target from the gold source sequence.
PreloadedDgold placed directly in context; no search tool.
Data analysisStandardWrites and runs SQL / Python through ordinary execution tools.
IdealCode runs without error, exactly as the agent intended.

Bring your own tool or variant

Every axis is an extension point: register your own planning, search, or data-analysis implementation and pass it as that axis's mode. This is how you measure a new retriever, planner, or executor against the idealized upper bound and the realistic baselines. 

# [FILL IN — exact CLI] ablate one axis, hold the others ideal
python -m sana.evaluation \
    --profiles profiles/ \
    --model gpt-5.4-nano \
    --plan ideal --search bm25 --data-analysis ideal \
    --budget 30 --out runs/search_bm25/

# plug in your own implementation on any axis
python -m sana.evaluation --search my_hybrid_retriever ...

3 sana-analysis

Analysis scores the runs and reproduces the paper's diagnosis. The primary metric is semantic match (SM) — an LLM-as-judge crediting answers equivalent to the gold answer up to formatting, aliases, units, or phrasing — alongside two discovery-recall metrics over the gold sources:

SM

Semantic match against the gold answer (↑), the headline metric.

D_ret

Retrieval recall: gold sources surfaced by the search tools (↑).

D_acc

Access recall: gold sources actually opened / queried (↑).

From the scored runs, analysis produces:

  • Per-component deltas — the SM gain from idealizing each axis (charted on the home page).
  • End-to-end comparison — Naive vs. Standard vs. all-Ideal runs.
  • Failure taxonomy — where incorrect runs break (source targeting, computation, finalization, …).
  • Plan-trajectory audit — whether the agent actually follows the plan it wrote.

If idealizing an axis closes a large gap, that component is the bottleneck. The gap that remains when all three are idealized is attributable to the agent's policy — evidence tracking, source commitment, intermediate validation, and stopping criteria. 

# [FILL IN — exact CLI] score runs and build the report
python -m sana.analysis --runs runs/ --out report/
