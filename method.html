Method

How SANA turns solved EQA tasks into runtime profiles, idealized tools, and a diagnosis.

Anatomy of an EQA task

An exploratory-QA task is a tuple τ = (Q, D, Dgold, T, A★, B): a question Q, a data lake D of structured and unstructured datasets, the minimal gold sources Dgold sufficient to answer it, a tool set T, the gold answer A★, and a tool-call budget B (we use B = 30).

Answering requires decomposing Q into subquestions (Q₁ … QK), discovering each one's gold dataset, and chaining intermediate answers so that Qi, digold, A₁…Ai−1 ⊨ Ai. The tools fall into two classes: dataset search f(q, k) over the lake, and data analysis g(c, d) that runs program c over dataset d.

The SANA profile

SANA annotates each solved task into a profile with three parts: a source sequence, sanitized subquestions (rewritten to not leak which dataset to fetch), and execution records (dataset, intent, query, and verified answer). Example, adapted from a LakeQA task:

{
  "task": "Compute the 2023 ratio of top-offense complaints to shootings in NYC's northernmost borough (rounded).",
  "source_sequence": ["The_Bronx", "nypd-complaints", "nypd-shootings"],
  "sanitized_subquestions": [
    "find NYC's northernmost borough",
    "count complaints there for the top 2023 offense",
    "count 2023 shootings there; divide (2)/(3), round"
  ],
  "execution_records": [
    { "src": "nypd-complaints", "intent": "count 2023 top-offense complaints in the Bronx",
      "query": "CNT(*) WHERE BORO='BRONX' & yr=2023 GRP_BY OFNS_DESC", "answer": 18613 },
    { "src": "nypd-shootings", "intent": "node_1_ans / 2023 Bronx shooting count",
      "query": "ROUND(18613 / CNT(*)) WHERE BORO='BRONX' & yr=2023", "answer": 42 }
  ]
}

Subquestion 1 only retrieves the The_Bronx dataset, so it has no execution record.

Idealized tools

SANA consumes the profile to construct one idealized tool per component. Each is a drop-in runtime tool, so the agent still decides when to call it.

plan_ideal

Receives the sanitized subquestion sequence and writes an explicit decomposition into the agent's system prompt.

search_ideal

Restricts the search space to Dgold; a metadata selector subagent returns only datasets matching the query intent (else "dataset not found").

execute_ideal

If the agent's intent matches the record (semantic judge), returns the verified answer; otherwise a stronger model generates and repairs code (≤ 2 retries) to fulfill the stated intent.

Condition space

Each run picks one mode per axis. Targeted ablations vary one axis while holding the others idealized.

AxisModeDescription
PlanningNaiveNo planning tool; the agent answers directly.
StandardPlanning tool, but a self-written plan with no sanitized sequence.
IdealReceives the sanitized subquestion sequence and stores a derived plan.
SearchNaiveBM25 sparse lexical search over the lake.
StandardHybrid search (RRF) with LLM table descriptions (Pneuma / AutoDDG).

PreloadedDgold placed directly in context; no search tool.
Data analysisStandardWrites and runs SQL / Python through ordinary execution tools.
IdealIntent-based execution tool that returns verified results.

Metrics

The primary success metric is semantic match (SM): an LLM-as-judge compares the submitted answer to the gold answer, crediting equivalent answers that differ in formatting, aliases, units, or phrasing. To study discovery separately, SANA also reports two recall metrics over the gold sources Dgold:

SM

Semantic match against the gold answer (↑).

D_ret

Retrieval recall: fraction of gold sources surfaced by the search tools (↑).

D_acc

Access recall: fraction of gold sources actually opened/queried via analysis tools (↑).

Runs use a budget of B = 30 tool calls and a 600 s cap (150 s per tool), orchestrated with the Strands Agent SDK over a DuckDB/Python sandbox. SANA's baseline is stronger than the original LakeQA setup (summarizing conversation manager, a strategy-nudge after repeated operations, and metadata-augmented search), so results are not a direct reproduction of LakeQA.
